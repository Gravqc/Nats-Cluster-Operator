# Test Nats-Cluster-Operator

1. Read the repository's `AGENTS.md`. Identify the changed behavior and compare the candidate with the commit or image that actually ran. Check `git status -sb` and inspect the relevant tests. Record the initial Kind state and restore it when finished.
2. Run the focused static checks. Controller or upgrade changes require `make test` (race tests and vet), Go formatting, and the relevant Kind checks. Use the repo virtual environment for Python unit tests and Ruff. Compare the generated CRD and chart CRD. If the host lacks Go, a local Go container with the pinned toolchain can run the checks.
3. Use `just up`, the repo's `.state/kubeconfig` and explicit `kind-nats-operator-dev` for runtime checks. Preserve an existing lab. Use a fresh test namespace with its own Helm-installed controller, synthetic `nats-auth` Secret, and fresh fixtures. The existing Python suites default to `nats-demo`. To run them in another namespace, make a scratch checkout or copy under `.state` and change only that namespace (and the probe image tag if needed) in the test copies. Link its kubeconfig to the repo kubeconfig and reuse the digest-checked chart archive. Use distinct local image tags for old and new controllers in transition tests. Keep evidence in `.state`. Clean up only fixtures created for this run.
4. Select checks for the behavior at risk:
   - **Reconciliation or rollout.** Run `tests/e2e.py`, `tests/memory.py`, and `tests/upgrade_comparison.py` for a full regression. Verify seeded and newly acknowledged payloads by content, independent clusters, retained storage, a blocked upgrade, a controller restart, and recovery after a confirmed process replacement. A metadata leader may retain its name.
   - **Config or shutdown transitions.** Test newly created one- and three-broker resources. A standalone upgrade interrupts availability, so verify payloads after the replacement mounts the same data. For an existing R3 cluster, seed a stream, switch the controller image alone, and check the ConfigMap and broker UIDs. Test the first guarded server rollout and a later restart of a replacement. Confirm old and new broker behavior by observing drain and exit with real connections, and verify all acknowledged payloads. Use distinct Job names at each phase because Job templates are immutable.
   - **Lag or measurement changes.** Run the focused Python unit tests and `tests/catchup_comparison.py` when applicable. Require current-generation stream health evidence while all pods are Ready. Check the publisher spans both windows, whether any restart happened while gated, and that all acknowledged messages verified. A chart gap below the fixed comparison threshold is inconclusive even when the operator gate behaves correctly.
   - **Drain thresholds.** Use `tests/lameduck.py baseline` for inherited timing, and `tests/lameduck_tradeoff.py A|B` when evaluating a timing change. Verify the effective arm, clean exits, reconnects, acknowledgement gaps, and payloads. Run timing arms without competing validation traffic where practical. Preserve missed thresholds and distinguish a probe retry gap from confirmed server downtime.
5. If a probe stalls, inspect the Job conditions and logs. A failed Job can leave a wait for completion running until its timeout. Keep the failed attempt's evidence and use fresh fixtures for a full retry. Create a separate scratch runner if the first runner is still active.
6. Report actual commands and outcomes, including threshold misses, retries, and limitations. Keep historical experiment evidence when rolling back an experimental behavior. Apply the user's separate commit and push instructions.
